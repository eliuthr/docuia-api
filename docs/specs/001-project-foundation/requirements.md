# 001 — Project foundation: requirements

> Phase 1 (week 1) of the DocuIA roadmap.
> Deliverable: a user uploads a PDF through the API and it is stored with status `pending`.

## Context

DocuIA receives documents (invoices, contracts, résumés), processes them in the background and
uses an LLM to extract data. This first spec only lays the foundation: configuration, local
infrastructure, file upload and status lookup. Queueing and processing arrive in spec 002.

## Scope

In scope:

- Local infrastructure with Docker Compose (MongoDB and Redis).
- Environment configuration validated at startup.
- `documents` module: upload a file, get one document, list documents.
- Pluggable storage (`StorageProvider`) and persistence (`DocumentRepository`) behind interfaces.
- `/health` endpoint, global error filter, Swagger docs, CORS for the web client.

Out of scope (later specs):

- Enqueueing jobs and the worker (002), LLM extraction (003), `ask` endpoint (004), agent (005),
  AWS implementations (006), JWT auth, rate limiting and CI (007).

## User stories and acceptance criteria

Criteria use the EARS format ("WHEN … THE SYSTEM SHALL …").

### US-1 — Upload a document

As an API client, I want to upload a document so that it can be processed later.

- **AC-1.1** WHEN a client sends `POST /documents` with a multipart field `file` containing a PDF,
  PNG or JPEG of at most `MAX_UPLOAD_SIZE_MB`, THE SYSTEM SHALL store the file, persist a document
  with status `pending` and respond `201` with the document representation.
- **AC-1.2** WHEN the file type is not PDF, PNG or JPEG, THE SYSTEM SHALL respond `400` and store
  nothing.
- **AC-1.3** WHEN the file exceeds `MAX_UPLOAD_SIZE_MB`, THE SYSTEM SHALL stop reading the upload,
  respond `413` and store nothing. _(Revised during implementation: was `400`; enforcing the limit
  in Multer avoids buffering oversized files, and 413 is the precise status.)_
- **AC-1.4** WHEN the request has no `file` field, THE SYSTEM SHALL respond `400`.
- **AC-1.5** WHEN persisting the document fails after the file was stored, THE SYSTEM SHALL delete
  the stored file and respond `500` without leaking internal details.
- **AC-1.6** THE SYSTEM SHALL NOT process the document inside the HTTP request.

### US-2 — Check a document's status

As an API client, I want to look up a document so that I know whether it is ready.

- **AC-2.1** WHEN a client sends `GET /documents/:id` with an existing id, THE SYSTEM SHALL respond
  `200` with the document representation.
- **AC-2.2** WHEN the id is not a valid UUID, THE SYSTEM SHALL respond `400`.
- **AC-2.3** WHEN no document has that id, THE SYSTEM SHALL respond `404`.

### US-3 — List documents

As a web client, I want to list recent documents so that I can show them to the user.

- **AC-3.1** WHEN a client sends `GET /documents`, THE SYSTEM SHALL respond `200` with the
  documents ordered by creation date, newest first, up to `limit` items (default 20, max 100).
- **AC-3.2** WHEN `limit` is not an integer between 1 and 100, THE SYSTEM SHALL respond `400`.

### US-4 — Operability

- **AC-4.1** WHEN a client sends `GET /health`, THE SYSTEM SHALL respond `200` with
  `{ "status": "ok" }`.
- **AC-4.2** WHEN a required environment variable is missing or invalid, THE SYSTEM SHALL refuse to
  start and log which variable failed.
- **AC-4.3** WHEN any error occurs, THE SYSTEM SHALL respond with
  `{ statusCode, error, message, path, timestamp }` and never include a stack trace.
- **AC-4.4** THE SYSTEM SHALL expose Swagger UI at `/docs` describing every endpoint.
- **AC-4.5** THE SYSTEM SHALL accept browser requests only from the origin set in
  `CORS_ORIGIN`.

## Document representation

```json
{
  "id": "6f1c…-uuid",
  "originalName": "invoice-001.pdf",
  "mimeType": "application/pdf",
  "sizeBytes": 48213,
  "status": "pending",
  "createdAt": "2026-10-22T18:00:00.000Z",
  "updatedAt": "2026-10-22T18:00:00.000Z"
}
```

Status lifecycle (only `pending` is used in this spec): `pending` → `processing` → `ready` | `failed`.

## Non-functional requirements

- **NFR-1** IDs are UUID v4 generated by the application, so they work the same on MongoDB and
  DynamoDB.
- **NFR-2** Services depend on `StorageProvider` and `DocumentRepository` abstractions; the
  implementation is chosen by configuration.
- **NFR-3** Unit tests for every service; e2e tests for every endpoint, with no external services
  required (in-memory repository and temp-dir storage).
- **NFR-4** `npm run lint`, `npm run test`, `npm run test:e2e` and `npm run build` pass.
